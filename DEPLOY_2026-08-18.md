# Deploying this release to Contabo

Covers PR **#82** (clients & patents) and PR **#83** (team spaces, BD pipeline, calendar,
reporting lines, appraisals). Written 18 August 2026.

> **Merge both PRs into `main` first.** The server pins itself to `main`; a branch left unmerged
> deploys nothing. #83 is branched off #82, so merge **#82 first**, then #83.

**Roughly 15 minutes**, most of it the rebuild. Nobody is logged out and there is no downtime
window — every migration is additive and the old build keeps serving until the new one is healthy.

## Step 1 — pull and rebuild

```bash
cd /root/pdash

# Fetch main with a FRESH token (never left in git config or shell history)
read -rs -p "GitHub token: " GHT; echo
git fetch "https://x-access-token:${GHT}@github.com/AnantSQIP/pdash.git" main
unset GHT
git checkout -B main FETCH_HEAD
git log --oneline -5          # confirm the new commits are actually here

# Rebuild. The api container runs `prisma migrate deploy` on start, so all 9
# migrations apply themselves.
docker compose -f docker-compose.prod.yml --env-file .env.production up -d --build
```

Wait for it to come up before running anything else — the commands below talk to the new build:

```bash
for i in $(seq 1 60); do
  curl -fsS http://127.0.0.1:3000/api/v1/health | grep -q '"db":"up"' && { echo HEALTHY; break; }
  sleep 3
done
```

## Step 2 — the four commands, in this order

Order matters: roles must exist before permissions are attached to them, and people must have
roles before reporting lines can be derived from seniority.

Set this once so the rest are readable:

```bash
DC="docker compose -f docker-compose.prod.yml --env-file .env.production"
```

### 2a. Roles — Ankit and Anant to Senior Consultant

```bash
$DC exec -T api node packages/db/prisma/dist/roster-align-2026-08.js
```

Expect two lines reading `Employee -> Senior Consultant`. Idempotent; safe to re-run. It also
reports anyone who has left — that is normal output, not an error.

### 2b. Permissions — grant the four new codes

**Required.** New codes are not granted by a migration.

```bash
$DC exec -T api node packages/db/prisma/dist/regrant-roles.js
```

Expect `Added 4 new permission code(s) from the catalog`, then these totals:

```
Super Admin 96 · Admin 94 · Manager 57 · Senior Consultant 51 · HR 51
Consultant 44 · Senior Research Associate 44 · Employee 40
```

Idempotent, runs in a transaction, does not wipe custom grants and logs nobody out.

### 2c. Reporting lines — the one that unblocks appraisals

```bash
$DC exec -T api node packages/db/prisma/dist/reporting-lines-2026-08.js
```

Expect about 25 `ADD` lines and `Mohit Kalra … ROOT`. It refuses to write if it detects a cycle.

> **Read the output.** These lines are DERIVED from seniority and project managers, not from a
> chart you gave me. One person may end up with a lot of direct reports. Correct real lines in the
> `OVERRIDES` map at the top of `packages/db/prisma/reporting-lines-2026-08.ts`, then re-run — it
> only writes what changed.

### 2d. Holiday calendar — nothing to run

The 2026 calendar and the four optional holidays are loaded **by the migration**, so they are
already in place after step 1. Verify in step 3.

## Step 3 — verify what actually landed

Don't trust the build log; ask the database.

```bash
$DC exec -T postgres psql -U pdash -d pdash -c "
  -- the four new permission codes
  select code from permission where code in
    ('team.view','team.manage','deal.view','deal.manage') order by code;

  -- reporting lines: was 0 before this release
  select count(*) as reporting_lines from user_manager;

  -- the two role changes
  select u.\"firstName\"||' '||u.\"lastName\" as person, r.name as role
    from \"user\" u join user_role ur on ur.\"userId\"=u.id join role r on r.id=ur.\"roleId\"
   where u.email in ('ankit.verma@squarkip.com','anant.gupta@squarkip.com');

  -- the 2026 calendar: 16 firm-wide holidays, 4 optional
  select type, count(*) from holiday group by type order by type;
  select count(*) as optional_holidays from optional_holiday where year = 2026;

  -- the new tables exist
  select table_name from information_schema.tables
   where table_name in ('team_task','deal','deal_activity','optional_holiday',
                        'optional_holiday_election','appraisal_parameter','appraisal_score',
                        'client_ledger_override')
   order by table_name;
"
```

Then in the browser, as a Super Admin: **Team Spaces** and **BD Pipeline** should appear in the
sidebar, and **Client Ledger** under Administration.

## If something looks wrong

```bash
$DC logs --tail=120 api          # migration failures surface here
$DC ps                           # every service should read Up
```

Every migration in this release is additive — new tables and nullable columns — with two
exceptions worth knowing:

- `task_list.projectId` **drops NOT NULL**. Existing rows keep their project and every query that
  filters on `projectId` is unaffected.
- `team.status` **is dropped**. Nothing ever wrote to that table outside this feature, so the
  column held nothing.

Nothing removes data. A rollback is `git checkout` of the previous commit plus a rebuild; the new
columns and tables simply stop being read.
