ChoicesThe three you asked for that I had advised against

You chose them, so they are done. Two are implemented differently from how the option described them, because there was a version without the downside I had objected to. That is a change to my proposal, so it is stated rather than buried.

07Logout — done, but without signing out your phoneFixed
The option said"Make logout revoke the access token immediately (signs you out on every device at once)."
Why I objectedTwenty-seven people signing out of a desk and losing their phone session daily is a worse cost than the risk it removes.
What I did insteadGave the access token the id of its own sign-in — the refresh-token family, which survives every rotation of that session. Signing out revokes that family; the middleware then refuses a token whose session is gone.
ResultYou get the immediate revocation you asked for, and other devices are untouched. Sign out everywhere still clears everything.
Safe to deployTokens issued before this carry no session id and stay valid until they expire, so shipping it does not sign the firm out.
10Validation before permission — the premise was wrongFixed
The option said"Reorder validation vs permission checks across all 363 routes."
The truthThat was not the cause, and I had it wrong in revision 1 too. The framework already checks permission before validating. These particular routes do their ownership check inside the service, which necessarily runs after validation — so the 400 arrived first.
What I didAdded a guard to the eleven individual-appraisal routes, which runs before validation. No reordering, no touching the other 350.
Why only appraisalsThe information exposed elsewhere is field names, which are already in the browser bundle. An appraisal is different: it carries somebody's rating and their manager's written remarks, so even confirming one exists is worth refusing.
09Team list creationFixed
Done as describedCreating a list returns the list, not the whole team space. The screen refetches separately, so nothing depended on the old shape — verified the created id is usable immediately.

UnaskedThree things the testing turned up

AYour demo link had been dead since 04:41Fixed
WhatThe tunnel process was running and its URL was unreachable — alive but not working, which is exactly what a process check misses. It had been in that state for about five hours.
FixedRestarted. New link: drainage-ann-smallest-valium.trycloudflare.com, answering in under a second.
Worth knowingThere is no supervisor and no scheduled task, so nothing would have restarted it. It stays up until something disturbs it.
BThat demo is showing the product as it was on 7 AugustYour call
WhatThe stack behind the tunnel runs an API built on 7 August, with a database to match: no reporting lines at all, no deals table, no appraisal parameters, no optional holidays, no policies, and a Business Development role that exists with zero permissions.
Not brokenOld code and old data agree with each other, and the old screens never call the routes that are missing. It works — it is just twelve days behind.
ButNothing built in Phase 2 is visible there: no client ledger, no team spaces, no BD pipeline, no departments screen, no org chart, no appraisal parameters. Anyone shown that link is being shown August the 7th.
To fixThat copy needs pulling, rebuilding and migrating — the same three steps as the server. It briefly interrupts the link, so it is your call when. The Contabo server is the copy that has been kept current.
CA rate limit worth watching, not yet a problemObservation
WhatThe limit is 200 requests a minute per address. Each person is counted separately through the proxy — I checked that, and it is set up correctly.
The catchIt counts by address, and an office shares one. Twenty-seven people behind a single gateway share 200 a minute, which is about seven each.
Honest statusNobody has reported this, and I could not test it without knowing your office network. If anyone ever sees a sudden "too many requests" that clears after a minute, this is the first place to look, and the fix is to count per signed-in person rather than per address.
Capacity is fineSixteen simultaneous sign-ins completed in 105 milliseconds with no errors.
