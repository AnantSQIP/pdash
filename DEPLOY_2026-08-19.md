## The commands

> **`-f docker-compose.prod.yml` is not optional.** The plain `docker-compose.yml` defines only
> postgres, redis and minio — no `api`, no `web`. Running `docker compose up -d --build` without
> the flag rebuilds nothing, leaves the old containers running, and every script below then runs
> against the OLD code and silently does nothing. Docker does warn you, as
> `Found orphan containers (pdash-web-1, pdash-api-1)` — that warning means the deploy is not
> deploying. The repository lives in `~/pdash`, not `/opt/pdash`.

```bash
ssh -p 2222 root@217.76.59.244
cd ~/pdash

# 1. Take the code, rebuild, restart. The migration runs on boot.
git pull origin main
docker compose -f docker-compose.prod.yml up -d --build

# 2. Wait for the API to be healthy before running anything against it.
#    The build compiles both apps, so give it several minutes.
docker compose -f docker-compose.prod.yml logs -f api      # Ctrl-C on "listening on"

# 3. Permissions, roster, reporting lines — IN THIS ORDER.
#    The role has to exist before anybody can be put on it, and people have to be on
#    their roles before the lines are drawn from them.
docker compose -f docker-compose.prod.yml exec api node packages/db/prisma/dist/regrant-roles.js
docker compose -f docker-compose.prod.yml exec api node packages/db/prisma/dist/roster-align-2026-08.js
docker compose -f docker-compose.prod.yml exec api node packages/db/prisma/dist/reporting-lines-2026-08.js

# 4. Optional — fills the policy library, which is currently empty.
docker compose -f docker-compose.prod.yml exec api node packages/db/prisma/dist/seed-policies-2026-08.js
```

If a step prints something else, stop and read it rather than carrying on.

**`regrant-roles`** — this is the step that tells you whether the rebuild happened at all.

not run.

## If something goes wrong

```bash
# What the API is actually doing
docker compose -f docker-compose.prod.yml logs --tail 100 api

# Did the image really rebuild? Compare this against when you ran the deploy.
docker inspect --format '{{.Created}}' $(docker compose -f docker-compose.prod.yml images -q api)

# Did the migration apply?
docker compose -f docker-compose.prod.yml exec postgres \
  psql -U pdash -d pdash -c "select name from _prisma_migrations order by finished_at desc limit 3;"

# Roll the code back — data is unaffected, the migration is additive
git reset --hard HEAD~1 && docker compose -f docker-compose.prod.yml up -d --build
```

### Stray containers from a wrong-file run

If `docker compose up` was run without the prod flag, it will have started `redis` and `minio`,
which production does not use. It reuses the existing postgres container rather than starting a
second one, so no data is affected. Remove the strays when convenient:

```bash
docker compose -f docker-compose.yml down
```

Nothing here deletes data. The migration only adds a column and an index, and every script is
written to be run more than once.
