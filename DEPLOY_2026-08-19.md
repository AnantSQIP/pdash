# Deploying to Contabo

Everything on `main` as of **19 August 2026**, `e532adf`.

> **Two flags, both required on every command. Neither is optional.**
>
> **`--env-file .env.production`** — the environment file is called `.env.production`, and Docker
> Compose only auto-reads a file named exactly `.env`. Without the flag every variable resolves to
> a blank string, `docker-compose.prod.yml` supplies defaults for none of them, and postgres fails
> its healthcheck because it runs `pg_isready -U` with no username. api and web then refuse to
> start behind an "unhealthy" dependency and **the site returns 502**. The database is never
> harmed — it lives in the `pgdata` volume and `POSTGRES_*` only matters at first initialisation —
> but the site goes down until the flag is supplied.
>
> **`-f docker-compose.prod.yml`** — the plain `docker-compose.yml` defines only postgres, redis
> and minio: no `api`, no `web`. Without this flag the build rebuilds nothing, the old containers
> keep running, and every script below then runs against the OLD code while appearing to succeed.
> Docker does say so, as `Found orphan containers (pdash-web-1, pdash-api-1)` — that warning means
> the deploy is not deploying.
>
> The repository lives in `~/pdash`, not `/opt/pdash`.

## The commands

```bash
ssh -p 2222 root@217.76.59.244
cd ~/pdash

# 1. Take the code and rebuild. Migrations run by themselves when the API container starts.
git pull origin main
docker compose --env-file .env.production -f docker-compose.prod.yml up -d --build

# 2. Wait until the API is genuinely up. The build compiles both apps — give it several minutes.
docker compose --env-file .env.production -f docker-compose.prod.yml logs -f api
#    Ctrl-C once it prints "listening on :4000"

# 3. Confirm postgres is HEALTHY before going further. Everything below depends on it.
docker compose --env-file .env.production -f docker-compose.prod.yml ps

# 4. Permissions, roster, reporting lines — IN THIS ORDER.
#    The role must exist before anybody can be put on it, and people must be on their
#    roles before the lines are drawn from them.
docker compose --env-file .env.production -f docker-compose.prod.yml exec api node packages/db/prisma/dist/regrant-roles.js
docker compose --env-file .env.production -f docker-compose.prod.yml exec api node packages/db/prisma/dist/roster-align-2026-08.js
docker compose --env-file .env.production -f docker-compose.prod.yml exec api node packages/db/prisma/dist/reporting-lines-2026-08.js

# 5. Optional — fills the policy library, which is otherwise empty.
docker compose --env-file .env.production -f docker-compose.prod.yml exec api node packages/db/prisma/dist/seed-policies-2026-08.js
```

Every script is safe to run more than once.

## Migrations — all automatic

The API image's start command is `prisma migrate deploy` followed by the server, so these apply on
boot. **You never run them by hand.**

| Migration | What it adds | From |
|---|---|---|
| `20260925090000_department_head_and_unique_name` | An explicit department head; one name per org | #86 |
| `20260926090000_deal_next_action_and_type` | Next-action date, note and expected work type on a deal | #93 |
| `20260927090000_task_completed_at` | When a task was actually finished, backfilled | #94 |
| `20260928090000_policy_versioning` | Which version of a policy somebody agreed to | #95 |

All four are **additive** — new nullable or defaulted columns, no data destroyed, nothing renamed.

Two are worth knowing about:

- **`20260925`** de-duplicates department names *before* creating its unique index, so it cannot
  fail on rows already in your table, and it backfills each department's head to whoever the old
  regex would have chosen. Nothing is lost.
- **`20260927`** backfills `completedAt` from `updatedAt` for tasks already closed — the same
  figure performance was already using, so no history changes on the day it ships. But where a
  batch of tasks was last edited on one day they all inherit that day and will read as late
  against older due dates. That is not a regression, it is what the on-time rate was already
  computing; the metric glossary says so in the app.

## If something goes wrong

```bash
# What the API is actually doing
docker compose --env-file .env.production -f docker-compose.prod.yml logs --tail 100 api

# Did the image really rebuild? Compare against when you ran the deploy.
docker inspect --format '{{.Created}}' \
  $(docker compose --env-file .env.production -f docker-compose.prod.yml images -q api)

# Which migrations have applied
docker compose --env-file .env.production -f docker-compose.prod.yml exec postgres \
  psql -U pdash -d pdash -c "select name from _prisma_migrations order by finished_at desc limit 6;"

# Roll the code back. Data is unaffected — every migration is additive.
git reset --hard HEAD~1
docker compose --env-file .env.production -f docker-compose.prod.yml up -d --build
```

### The site is returning 502

Almost certainly the missing `--env-file .env.production`. Check for blanks:

```bash
docker compose --env-file .env.production -f docker-compose.prod.yml config | grep POSTGRES_USER
```

If that shows a real value **with** the flag and a blank **without** it, that is the whole problem.
Re-run step 1 with the flag. Your data is untouched — confirm the volume is still there with
`docker volume ls | grep pgdata`.

### Stray containers from a wrong-file run

If `docker compose up` was ever run without the prod flag it started `redis` and `minio`, which
production does not use. It reuses the existing postgres container rather than starting a second
one, so no data is affected. Remove the strays when convenient:

```bash
docker compose -f docker-compose.yml down
```

## Worth fixing properly, when there is time

`docker-compose.prod.yml` interpolates six variables and declares defaults for none, and does not
name an `env_file`. That is why a missing flag takes the whole site down instead of failing loudly
at configuration time. Adding `env_file: .env.production` to each service, plus sensible defaults,
would make `docker compose config` refuse rather than silently substituting blanks — and would make
both flags above unnecessary.
